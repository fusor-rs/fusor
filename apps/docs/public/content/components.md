# Reusable HTML

Build two counters from one Rust module and one HTML template. Follow every file from the
parent page to the elements each child renders.

## 1. Define the counter state {#typed-inputs}

`src/counter.rs` defines the child component’s state. The `count` signal comes from its
parent; `clicks` belongs to this particular counter.

`#[input]` marks a parent-supplied field. `#[local(init = signal(0))]` initializes private
state separately for each new instance.

`#[derive(FromInputs)]` reads those annotations and generates the `CounterInputs` type and
the construction code that connects the fields. You do not need to write that second struct
or implement the constructor contract yourself for this component.

The `#[...]` syntax is a Rust attribute: information read by the compiler or a macro when
generating code.

The `template!` path is relative to `Cargo.toml`, not to `src/counter.rs`. It connects this
module to the HTML file shown in the next step; it does not create that file.

```rust source=../../crates/fusor-cli/template/counter.rs title=src/counter.rs · complete file
```

## 2. Write the HTML the counter renders {#counter-template}

Create or open `web/components/counter.html` with these contents. The declaration
`rust:component="Counter"` pairs this template with the `Counter` type above.

Within it, `state` is that particular `Counter` instance: `state.count` and `state.clicks`
refer to its Rust fields. Each `<Counter>` inserts the `<section>` and everything inside it.

The `<template>` wrapper declares the reusable HTML and does not appear on the page.

```html source=../../crates/fusor-cli/template/counter.html title=web/components/counter.html · complete file
```

> The braces in `on:click` group two Rust statements into one handler, so the button updates
> both signals. The paragraphs that read them update automatically. This reusable file has
> one native HTML root: section.

## 3. Import the counter in the parent {#parent-state}

The parent `App` creates one count signal. `use crate::counter::Counter` makes the child

module to the page in the next step. Rust modules import types; the HTML files do not import
each other.

```rust source=../../crates/fusor-cli/template/app.rs title=src/app.rs · complete file
```

## 4. Place two counters in the page {#component-tags}

The file `web/index.html` starts the application with `<App>` and uses `<Counter>` twice.
Each counter tag creates a separate instance from the same HTML template.

The input `count="{{ state.count.clone() }}"` passes another handle to the parent’s existing
signal. It does not copy the number.

Here `state` means the Rust `App` value. Inside `counter.html`, it means that child’s
`Counter` value. Use a closing tag for each component.

```html source=../../crates/fusor-cli/template/index.html title=web/index.html · complete file
```

> The `Counter` tag resolves through the Rust import in `app.rs`. Its input name count must
> match `CounterInputs.count`, and its value must have that field’s Rust type. rustc reports
> missing, unknown, or wrongly typed inputs.

## How the files connect {#connection}

The `template!` association connects a Rust module to authored HTML at build time. The
imported Rust type determines which component a tag constructs. The browser receives the
child’s native elements at that position; `Counter` is not an extra wrapper element.

```text title=Diagram · file and render connections, not code
src/lib.rs
  mod app → src/app.rs → template!("web/index.html")
                         use crate::counter::Counter
                                  ↓
                         <Counter count="…"></Counter>
                                  ↓
  mod counter → src/counter.rs → template!("web/components/counter.html")
                                  ↓
                         <template rust:component="Counter">
                           <section class="counter">…</section>
                         </template>
```

## Choose shared state or a snapshot {#inputs}

Pass a `Signal<T>` when a retained child should follow later changes, as `Counter` does.
Calling `.clone()` shares the signal handle; calling `.get()` reads a snapshot of its
current value.

Input expressions and constructors run when an instance is created. A normal reactive update
does not reconstruct the child. An `i32` input, for example, keeps the number it received at
construction.

> For this `Counter`, `count="{{ state.count.get() }}"` is a type error because the input
> requires `Signal<i32>`. Plain attributes pass static Rust strings; use `{{ ... }}` for
> other Rust values.
>
> Input names match Rust field names exactly, such as `selected_id`. Even an `Option<T>`
> input must be supplied: pass `{{ None }}` when it has no value. Local initializers run
> once, in field declaration order.

## What the derive generates {#derive-rules}

For `Counter`, the derive generates a `CounterInputs` struct with a public `count` field. It
also implements `FromInputs`, the trait the framework calls to construct a component. A Rust
trait is an interface: a set of functions a type promises to provide.

The generated input struct has the same visibility as `Counter`. The original component
fields stay private. Every field must have exactly one `#[input]` or `#[local(init = ...)]`
annotation; missing or conflicting annotations produce a compiler error on that field.

```rust title=Rust · generated input contract, do not add this to your module
pub struct CounterInputs {
    pub count: Signal<i32>,
}
```

> The derive is available with the `derive` feature through `fusor::prelude::*`, without
> browser dependencies. The `dom` feature also enables it. Its associated `Error` is
> `std::convert::Infallible`. It supports concrete named-field structs and unit structs. It
> creates no `new()` method and does not replace `template!`. Reserve the generated
> `CounterInputs` name; do not also declare it yourself.

## Write the constructor when you need custom setup {#manual-inputs}

Local initializers can call ordinary Rust helpers such as `signal(0)` or
`Self::initial_clicks()`. They cannot read other fields of an instance still being
constructed, and they do not receive special inputs or owner variables.

When setup depends on parent inputs or needs an `OwnerHandle`, implement `FromInputs`
yourself. The file below is the complete manual equivalent of the derive example. Replace
only `src/counter.rs`; keep the same HTML and parent files. The application behaves
identically.

Use either this implementation or the derive, not both.

`FromInputs` is a renderer-independent construction trait. It has `Inputs` and `Error`
associated types and is available without features. Existing manual browser implementations
migrate by adding `type Error = fusor::dom::JsValue;`; their existing return signatures and
the compatibility import `fusor::dom::FromInputs` keep working. Portable constructors choose
their own error type.

Browser component tags convert errors through `fusor::dom::IntoMountError`: JavaScript
errors retain their original value, `Infallible` cannot fail, and `String` or `&str` become
JavaScript strings. Implement that trait for a custom error when enabling browser rendering.
Explicit mounting closures can call `.map_err(fusor::dom::IntoMountError::into_mount_error)`
themselves.

Construction and mounting remain separate. Ordinary effects still run immediately during
ordinary construction; owner activation gates work registered with `on_activate`. Moving the
trait does not change either lifecycle.

```rust source=tutorial/lessons/manual-inputs/counter.rs title=src/counter.rs · complete alternative
```

> `OwnerHandle` is a handle to a component’s lifetime, useful for requests and cleanup that
> should stop when it is removed. For a component tag, the framework calls
> `FromInputs::from_inputs` with the inputs and that child’s handle.
>
> The \_owner parameter in this example is an ordinary Rust parameter; the leading
> underscore says this counter does not use it. Generic components also use the manual trait
> in this release.

## Multiple roots without a wrapper {#fragments}

A reusable template can contain several native HTML root elements. They form a fragment:
one component instance owns all the siblings, without an extra element in the page.
For example, a component used inside a table row can render two cells:

```html
<template rust:component="PriceCells">
  <td>$25</td>
  <td>In stock</td>
</template>
```

The matching Rust type and `template!` association follow the same rules as `Counter`.
Use `<PriceCells></PriceCells>` inside a `<tr>`. Bindings, inputs, conditional mounting,
keyed rows, slots, and cleanup apply to the entire fragment. Shared templates hydrate
the existing siblings in place.

Templates require at least one native root. Put text and component tags inside those
roots. `<App>`, `<Async>`, and `<Await>` retain their single-root rules. JavaScript component
modules and island entry components require a single root; nested components can be fragments.

For manual DOM integrations, `Scope::root()` returns `Result<&Element, JsValue>`:
use `scope.root()?` for a single-root view. A fragment has no single element, so `root()`
and selector-based `select()` return an error. `attach()` and `attach_at()` place the whole
view, and `is_detached()` reports whether it remains in its preparation storage.
