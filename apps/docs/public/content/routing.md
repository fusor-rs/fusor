# Routing and navigation

Declare which HTML belongs at each URL. Compose nested routers through ordinary components,
even when their HTML lives in another file.

## Start with two pages and a fallback {#setup}

This example replaces the main page of the generated `my-app` from Installation. Keep its
`build.rs` and existing dependencies.

Add the dependency below under `[dependencies]`. In `[package.metadata.fusor]`, add
`history-fallback = ["/articles", "/missing"]`.

Create the five files below. The build discovers `web/components/pages.html`; a `template!`
call in its associated Rust module connects that HTML to the page types.

```toml title=Cargo.toml · add under [dependencies]
fusor-router = { version = "=0.1.5", features = ["browser"] }
```

> Use the same framework version as the app generated by your CLI.

## Select the HTML for the current URL {#html}

`<Router>` renders the children of the best matching `<Route>`. At `/articles/42`, the `:id`
segment captures `"42"`.

The attribute `let="params"` declares a local capture object inside that route. Its
`params.id` field is a decoded `String` passed to `Article`. You choose the local name
`params`.

A route marked `fallback` renders only when no sibling matches. Neither `<Router>` nor
`<Route>` creates a wrapper element.


## Put a nested router in another file {#nested}

Add a parent route ending in `/*`. It consumes its prefix and delegates the remaining path
to routers inside its mounted children.

`Dashboard` is an ordinary component imported into `src/app.rs`. It can live in its own Rust
module and HTML file. The root router is still the only browser-history owner.

```html title=web/index.html · add inside Router
<Route path="/dashboard/*">
  <Dashboard></Dashboard>
</Route>
```

> Also add "`/dashboard`" to `history-fallback` for direct document requests.

## Define the separate Dashboard component {#nested-state}

Add `mod dashboard`; to `src/lib.rs` and `use crate::dashboard::Dashboard`; to `src/app.rs`.
This component has local state so you can see retention: its count survives navigation
between its child routes.

```rust title=src/dashboard.rs · complete file
use fusor::{FromInputs, Signal, signal};

#[derive(FromInputs)]
pub struct Dashboard {
    #[local(init = signal(0))]
    count: Signal<i32>,
}

fusor::template!("web/components/dashboard.html");
```

## Match only the remaining path {#nested-html}

At `/dashboard`, the remaining path is empty, so `path=""` matches. At
`/dashboard/settings`, `path="settings"` matches. The nested fallback handles
`/dashboard/unknown`.

This `<Router>` receives its prefix through component ownership, including across files. It
needs no additional registration. Repeat the same pattern for deeper nesting.

```html title=web/components/dashboard.html · complete file
<template rust:component="Dashboard">
  <section>
    <h1>Dashboard</h1>
    <button on:click="state.count.update(|n| *n += 1)">
      Clicks: {{ state.count.get() }}
    </button>
    <nav>
      <a data-fusor-link href="/dashboard">Overview</a>
      <a data-fusor-link href="/dashboard/settings">Settings</a>
    </nav>
    <Router>
      <Route path=""><p>Overview</p></Route>
      <Route path="settings"><p>Settings</p></Route>
      <Route fallback><p>Dashboard page not found</p></Route>
    </Router>
  </section>
</template>
```

> The URLs in this example assume base-path = "/". Anchors follow browser URL resolution;
> their href is not automatically relative to the nearest `Route`.

## Understand matching and page lifetime {#matching}

`Route` paths accept literal segments, `:name` captures, and a final `/*` for nested
routing. Literal segments take precedence over captures. An exact match takes precedence
over an otherwise equal delegated pattern, regardless of declaration order. Ambiguous
siblings and duplicate fallbacks are build errors.

Trailing slashes are equivalent. Captures are decoded once, after splitting the path into
segments: `a%2Fb` becomes the single value `"a/b"`. A router with no match and no fallback
renders nothing.

```html title=HTML · Team is an application-defined component
<Route path="/teams/:team/*" let="params">
  <Team team="{{ params.team }}"></Team>
</Route>
```

> Changing a captured path parameter replaces that route’s view. Changing only the remaining
> path of a delegated route preserves its parent view and updates the nested router. Leaving
> a branch disposes it; returning creates a fresh instance.
>
> Query and fragment changes preserve matched pages. Fallbacks retain on query changes and
> replace on path changes. There is no hidden page cache.

## Read the current URL from Rust {#location}

In a component constructor, `owner` is the `OwnerHandle` supplied by `FromInputs`.

`Navigation::from_owner` finds the routing context provided before that page is constructed.
`location()` is a reactive `Derived<AppUrl>`; read it in a binding or resource key to react
to query changes. Construct an `AppUrl` with `AppUrl::parse`; its encoded components are
read-only. `path()` includes the leading slash; `query()` and `fragment()` omit `?` and `#`.

A newly prepared page sees the destination URL immediately. The lookup is explicit, so
components outside a router can handle its absence.

```rust title=Rust · inside a fallible constructor
use fusor_router::browser::declarative::Navigation;

// Inside a component constructor receiving owner:
let navigation = Navigation::from_owner(&owner)
    .ok_or_else(|| wasm_bindgen::JsValue::from_str("missing router"))?;
let location = navigation.location();
// Store location on your component. In a reactive closure:
// location.get().query_first("sort").unwrap_or_else(|| "recent".into())
```

## Navigate from an event or action {#navigate}

Prefer real anchors for links. For programmatic navigation, retain `Navigation` in component
state and call `navigate_url` after activation.

`NavigateOptions::default()` pushes a history entry; `replace: true` replaces the current
entry. `keep_focus` and `keep_scroll` can preserve a query control’s interaction.

URLs follow browser resolution and must remain inside the same origin and configured base.

```rust title=Rust · after the component has activated
use fusor_router::browser::NavigateOptions;

navigation.navigate_url("/articles/42", NavigateOptions::default())?;
```

> The router stages a replacement before changing history or discarding the old view.
> Preparation errors retain the old view and URL. `last_error()` exposes listener-driven
> failures. Constructors should avoid unrelated side effects; arbitrary application side
> effects cannot be rolled back.

Native fragment changes prepare their destination before updating router history metadata.
If preparation fails, the router retains the view and restores its URL. A failed back or
forward navigation returns to the shown entry; if restoration does not complete within
two seconds, or dispatching or restoring history fails, the router reloads the browser's
current URL. History access and focus failures
are reported through `last_error()`. Focus failures leave the committed navigation visible.

## Load data in the page that needs it {#data}

Routing selects and owns a page; data loading stays in your application. Create a `Resource`
in the page’s `FromInputs` constructor with its supplied owner.

Store `Navigation.location()` when query changes should reload that resource. Leaving the
page disposes its owned work. The reader example combines these APIs with loading/error UI
and refresh.

```sh title=Terminal · repository root
fusor dev --package fusor-navigation --port 8093
# Open http://127.0.0.1:8093/reader/
```

## Make direct links work after deployment {#hosting}

The CLI dev/serve commands honor `history-fallback`. Your production host needs equivalent
rules: serve `index.html` for document navigation under these prefixes, and actual 404s for
missing assets and API endpoints.

At a non-root base, route patterns stay application-relative; anchors and `navigate_url`
need URLs including that base. Use the configured `FUSOR_BASE_PATH` for static link helpers,
or a typed `Route` with `BasePath::href` for checked link generation.

```toml title=Cargo.toml
[package.metadata.fusor]
entry = "web/index.html"
assets = { "/" = "public" }
output = "dist"
base-path = "/"
history-fallback = ["/articles", "/dashboard", "/missing"]
```

> These are browser SPA routes. The static server’s fallback response has HTTP 200, even
> when a `Route` fallback displays a not-found page. SSR routing and automatic per-route
> bundle splitting are not included.

## Build a custom router when you need one {#custom}

The HTML API uses `fusor_router::browser::declarative::ViewRouter` to own matching and view
replacement. This is separate from the browser History API adapter, so `ViewRouter` can also
serve embedded panels or a custom URL source.

`RouteView` supplies lazy view factories. `NavigationDriver` stages a transition;
`PreparedNavigation` commits it. Dropping a staged transition rolls it back. Only one
transition per tree can be staged at a time. Complete it synchronously before yielding to
the browser, because preparation temporarily inserts inactive DOM.

The lower-level typed `Router<R>`, `Route`, and `Content` APIs remain available for
integrations. Ordinary applications can use the HTML API shown above.

> `<Router>` is browser-only and cannot be declared inside coherent `<Async>` or `<Await>`
> regions, or in server/shared templates. A matched page may contain `<Async>` and
> `<Await>`. Nested routers share navigation; they do not create independent browser
> histories.
